## 1. Defect Description
On sharp mountain curve frames (such as canyon roads) or road sections where heavy surface sun-glare washed out the asphalt, fewer than 3 pixel dots were detected for the right lane line. Executing `np.polyfit(y, x, 2)` threw `np.RankWarning: Polyfit may be poorly conditioned` and caused an unhandled `ZeroDivisionError: float division by zero` during curvature radius estimation ($R = \frac{(1 + (2Ay + B)^2)^{3/2}}{|2A|}$ when the road is nearly straight and $A \approx 0$).

## 2. Steps to Reproduce
1. Ingest curved mountain canyon frame (`curved_canyon.jpg`) or synthetic glare-occluded frame.
2. In `src/detector.py`, execute `fit_polynomial_splines()`.
3. Candidate pixel count for the right boundary falls below 3.
4. Observe warning and division-by-zero crash during tangent radius calculation.

## 3. Expected vs. Actual Behavior
- **Expected:** The ADAS perception pipeline must defensively validate candidate pixel density and compute curvature radii without mathematical singularities or application crashes.
- **Actual:** Execution raised `RankWarning` and crashed with `ZeroDivisionError`.

## 4. Root Cause Analysis
The polynomial fitting function called `np.polyfit` unconditionally without checking if the detected pixel count $N \ge 3$. Furthermore, when a road is nearly straight (tangent line where $A \approx 0$), dividing by $|2A|$ resulted in floating-point division by zero.

## 5. Developer Resolution (Applied by Software Developer Agent)
- Added defensive candidate density validation: Enforces $N \ge 50$ pixels before invoking `np.polyfit`.
- Implemented historical coefficient fallback: If pixel count is insufficient, smoothly falls back to the previous frame's historical polynomial from the memory buffer.
- Added denominator clamping in curvature calculation:
  ```python
  denom = max(abs(2.0 * A), 1e-6)
  radius = float(np.clip(((1.0 + (2.0 * A * y_eval + B) ** 2) ** 1.5) / denom, 10.0, 10000.0))
  ```
